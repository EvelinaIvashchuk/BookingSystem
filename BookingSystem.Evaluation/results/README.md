# Результати експериментів

Проєкт `BookingSystem.Evaluation` запускає ті самі `AgentService` і `KnowledgeSearch`, що й вебзастосунок,
але на окремій базі `bookingsystem_eval` з детермінованим автопарком (50 авто, 6 бронювань) і
з фіксованим «сьогодні» для кожного сценарію (середа, 2026-11-18, Europe/Kyiv).

## Як відтворити

```bash
# 1. База для експериментів + індексація бази знань (ембединги Gemini)
dotnet run --project BookingSystem.Evaluation -- index

# 2. E3 — пошук (налаштування параметрів лише на dev, оцінка на test)
dotnet run --project BookingSystem.Evaluation -- retrieval --tune-on dev --eval-on test

# 3. E1 — порівняння моделей (slot filling увімкнено); model@N — кількість повторів для моделі,
#    --max-cost — зупинити платні моделі, коли сума cost_usd у CSV досягне ліміту
dotnet run --project BookingSystem.Evaluation -- agent --models gemini:gemini-3.8-flash@3,gemini:gemini-3.6-flash@3,gemini:gemini-3.5-flash-lite@3,gemini:gemini-3.1-flash-lite@3,groq:openai/gpt-oss-120b@1,groq:openai/gpt-oss-20b@1,groq:qwen/qwen3.8-27b@1 --max-cost 5.90

# 4. E2 — ablation slot filling: запускається лише «off»; «on» береться з рядків E1 тієї ж моделі
dotnet run --project BookingSystem.Evaluation -- ablation --models gemini:gemini-3.8-flash@3,gemini:gemini-3.5-flash-lite@3 --max-cost 5.90

# 5. Підсумки (summary_agent*.csv) і графіки
dotnet run --project BookingSystem.Evaluation -- summary
python3 -m venv tools/.venv && tools/.venv/bin/pip install matplotlib
tools/.venv/bin/python tools/plot.py

# (за потреби) застосувати поточний критерій уточнення до вже записаних рядків
dotnet run --project BookingSystem.Evaluation -- rescore
```

Команди `agent`, `ablation` та `index` на старті очищають чат-сесії та чернетки в `bookingsystem_eval`,
тому одночасно можна запускати лише одну з них; `summary` і `rescore` базу не чіпають.

Прогони агента відновлюються з місця зупинки: рядки, які вже є в `agent_runs.csv`, пропускаються.
Тимчасові помилки провайдера (429, 5xx, тайм-аути) повторюються з експоненційною затримкою; якщо
вичерпано денну квоту моделі, прогін цієї моделі зупиняється — достатньо повторити ту саму команду пізніше.

## E3. Пошук у базі знань — прогін 2026-11-18

База знань: 12 документів, 110 фрагментів; ембединги `gemini-embedding-001` (3072);
повнотекстовий пошук — MySQL FULLTEXT (natural language mode) по стемованому тексту.
Запити: 56 (28 коротких термінових, 28 описових; 7 англійською), dev = 17, test = 39.

**Важливо для методології.** Сітку v1 було задано заздалегідь. Після першого прогону розбивка за типами
запитів показала (і на dev, і на test), що повнотекстовий пошук погано працює для описових запитань
(dev: 0.297), а межі v1 не дозволяють зменшити його вагу (нижня межа w_ft = 0.15, слабкий штраф за довжину).
Тому додано сітку v2 — надмножину v1 з нижчою MinWeight (0–0.05) і сильнішим штрафом c (до 0.3).
Вибір параметрів, як і раніше, робиться лише на dev; test для вибору не використовується. Але рішення
розширити сітку ухвалено після перегляду результатів, тож у записці варто навести обидва варіанти.

**Висновки E3:**
1. На коротких термінових запитах адаптивне злиття найкраще з усіх методів (MRR@10 = 1.000 на test і 0.926 на dev
   проти 0.974 / 0.870 у Vector та RRF) — гіпотеза про перевагу повнотекстового пошуку для термінів підтверджується.
2. На описових запитаннях повнотекстовий пошук слабкий, і будь-яке злиття з ним програє чистому векторному пошуку.
   Адаптивні ваги з v2 зменшують цю шкоду порівняно з RRF (0.795 проти 0.784), але не усувають її.
3. Загалом на цій невеликій базі (110 фрагментів) із сильними багатомовними ембедингами найкращий —
   чистий векторний пошук; класичний RRF значуще гірший за нього (ДІ не містить 0).
   Різниця Adaptive v2 − RRF додатна, але статистично не значуща (39 запитів).
4. Англійські запити повнотекстовий пошук не знаходить зовсім (MRR = 0) — стемер і база знань українські.

**Обмеження та зміни методики (важливо для записки):**

1. **Groq — 1 неповний повтор.** Free tier дає 200K токенів на день на модель, а повний прогін однієї моделі — ≈ 370–390K,
   тому gpt-oss-120b пройшов 69, gpt-oss-20b — 66, qwen3.8-27b — 49 з 74 сценаріїв (сценарії йдуть по порядку,
   тож faq, booking та out-of-scope покриті частково або зовсім ні). Прогін відновлюється тією самою командою.
   Затримки Groq включають очікування через ліміт токенів на хвилину: у qwen один хід тривав 605 с,
   тому середнє (13.7 с) непоказове, медіана — 0.8 с.
2. **Gemini 3 і `thought_signature`.** Перший smoke-прогін Gemini падав з HTTP 400: Gemini 3 вимагає повертати
   підпис міркувань разом із викликом інструмента, а OpenAI SDK його відкидає. Виправлено до основних прогонів
   (`GeminiThoughtSignatureHandler`); усі рядки E1/E2 записано вже з виправленням.
3. **Вартість Gemini.** OpenAI-сумісний API Gemini не включає «thinking»-токени в `completion_tokens`
   (лише в `total_tokens`), тому спочатку вартість 3.6/3.8-flash занижувалась ≈ 1.34× (lite-моделі майже не «думають»).
   Облік виправлено під час прогону (`output = max(output, total − input)`). Для 3.6-flash і 3.8-flash у таблиці
   токени й вартість — лише з рядків після виправлення (повтори 2–3 і E2); на метрики якості це не впливає.
   Фактичні витрати на всі прогони E1 + E2 разом зі smoke-перевірками за білінгом Google AI Studio — **$5.91**
   (листопад 2026); оцінка за записаними токенами з поправкою на «thinking» — ≈ $5.95, тобто облік точний до ~1%.
4. **Критерій уточнення змінено після перегляду результатів.** Спочатку відповідь вважалась уточненням лише зі
   знаком «?» і з вузьким словником ключових слів. Перегляд провалів показав, що всі вони — коректні уточнення
   у формі ввічливого прохання («Будь ласка, вкажіть дати оренди…», «Вкажіть дату видачі та повернення…»).
   Критерій розширено: знак питання **або** дієслово-прохання («вкажіть», «уточніть», «зазначте», «please specify»…)
   і синоніми слотів («видачі», «взяття», «забрати», «закінчення»…). Команда `rescore` застосувала його до всіх рядків
   однаково. Зміна зарахувала 139 з 252 рядків сценаріїв `incomplete`; зворотних змін (успіх → провал) немає.
   Для прозорості — Task success за старим критерієм:

   | | 3.8-flash | 3.6-flash | 3.5-flash-lite | 3.1-flash-lite | gpt-oss-120b | gpt-oss-20b | qwen3.8-27b |
   |---|---|---|---|---|---|---|---|
   | старий критерій | 0.937 | 0.878 | 0.838 | 0.797 | 0.855 | 0.758 | 0.408 |
   | новий критерій | 0.986 | 0.986 | 0.946 | 0.928 | 0.913 | 0.894 | 0.510 |

   Порядок моделей за обома критеріями той самий.

**Висновки E1:**
1. Найкраща якість — у gemini-3.8-flash і gemini-3.6-flash (Task success 0.986, усі аргументи правильні). Єдиний їхній
   «провал» — сценарій B-05 (див. випадок 4 нижче). 3.6-flash при цьому вдвічі швидший (4.6 с проти 7.5 с на хід)
   за майже однакової ціни.
2. Lite-моделі Gemini лише на 4–6 п. п. гірші, але в 3–4 рази дешевші й у 2.7–5 разів швидші (1.5–1.7 с на хід).
   Їхні помилки зосереджені в бронюванні (booking 0.33–0.67) і відносних датах.
3. gpt-oss-120b / 20b на безкоштовному Groq близькі до lite-моделей Gemini (0.91 / 0.89 на пройденій частині)
   за найменшої затримки; повторів поки немає, тож різниця з lite-моделями в межах невизначеності.
4. qwen3.8-27b для агента непридатний: у 23 з 37 сценаріїв, де потрібен інструмент, він відповідає без виклику
   і вигадує авто та ціни.
5. Неповні запити всі моделі обробляють добре (Clarification ≈ 1.0). Лише раз за E1 модель вигадала відсутню дату:
   3.1-flash-lite на «I need a car from December 10» сама поставила повернення 11 грудня й виконала пошук.
   Slot filling цього не блокує — валідатор перевіряє формат, межі й узгодженість дат із текстом (дні тижня,
   тривалість), але не те, чи користувач узагалі назвав дату повернення. Це відоме обмеження внеску.

## E2. Ablation slot filling — прогін 2026-11-18

Ті самі 74 сценарії, 3 повтори, `Ai:SlotFilling:Enabled = false` (інструменти виконуються з аргументами моделі як є,
без злиття з відомими слотами, попередньої перевірки та блоку відомих параметрів у промпті; валідатор працює в
тіньовому режимі лише для метрик). Умова «on» — рядки E1 тієї самої моделі.

| Модель | Slot filling | Task success | Tool selection | Arg. accuracy | Clarification | Провалів (із 222) |
|---|---|---|---|---|---|---|
| gemini-3.8-flash | on | 0.986 ± 0.000 | 0.986 ± 0.000 | 1.000 ± 0.000 | 1.000 ± 0.000 | 3 |
| gemini-3.8-flash | off | 0.986 ± 0.000 | 0.986 ± 0.000 | 1.000 ± 0.000 | 1.000 ± 0.000 | 3 |
| gemini-3.5-flash-lite | on | **0.946 ± 0.000** | 0.973 ± 0.000 | 0.963 ± 0.000 | **1.000 ± 0.000** | 12 |
| gemini-3.5-flash-lite | off | 0.928 ± 0.021 | 0.959 ± 0.014 | 0.957 ± 0.011 | 0.944 ± 0.048 | 16 |

Графік: `charts/e2_slot_filling_ablation.png`.

Різниця для 3.5-flash-lite за сценаріями: без slot filling додатково провалюються M-09 (2 з 3), I-02 (2 з 3) і
R-03 (1 з 3); зі slot filling — на один раз більше C-08. Invalid Call Rate в обох режимах ≈ 0: моделі Gemini майже
не пропонують аргументів, які валідатор вважає невалідними (3.5-flash-lite — 2 перехоплені виклики на 180).

**Висновки E2:**
1. Для сильної моделі (3.8-flash) slot filling не змінює результат — ефект стелі: модель сама тримає контекст
   і не вигадує параметрів.
2. Для слабшої моделі (3.5-flash-lite) slot filling підвищує Task success з 0.928 до 0.946 і робить поведінку
   стабільною між повторами (std 0 проти 0.021). Явний внесок механізму видно в M-09: пам'ять параметрів
   між ходами повертає забуте обмеження ціни. В I-02 без slot filling модель двічі вигадала дату повернення,
   а зі slot filling щоразу питала; блокування тут не спрацьовувало (див. висновок 5 E1), тож різниця, імовірно,
   від блоку відомих параметрів у промпті або випадкова. Загалом різниця невелика (4 провали з 222; за сценаріями
   3 гірші без slot filling проти 1 гіршого з ним, знаковий тест не значущий) — це тенденція, а не доведений ефект.
3. Ціна і затримка в обох режимах однакові: перевірка слотів локальна й не додає викликів моделі.

## Якісний аналіз характерних помилок (з `agent_runs.csv`)

1. **Галюцинація замість виклику інструмента (qwen3.8-27b, S-01…S-05).** На «Потрібен автомат на 5 місць
   з 20 по 25 грудня» модель одразу відповідає списком «Toyota Camry — 2500 ₴/день…» без жодного виклику
   `search_available_cars`. Таких авто та цін у базі немає. Відтворено на точному запиті агента; спрощення схеми
   інструментів і параметри reasoning не допомагають. Системне правило «авто й ціни — лише з результатів
   інструментів» модель ігнорує; захист можливий лише архітектурний (наприклад, показувати картки авто тільки
   з результатів інструментів, як і зроблено у віджеті).
2. **«Авто недоступне», хоча воно вільне (lite-моделі, B-05, B-06).** На «Забронюй Toyota Camry з 10 по 12 грудня»
   модель шукає без фільтрів, отримує 5 найдешевших авто, не бачить серед них Camry і робить висновок, що вона
   зайнята. Сильніші моделі звужують пошук категорією й знаходять авто. Можливе покращення — параметр моделі/марки
   в `search_available_cars` або підказка в описі інструмента.
3. **Плутанина ідентифікаторів (gemini-3.1-flash-lite, B-01, B-04).** На «Беру найдешевший» модель пише
   «Ви обрали Citroen Berlingo», але передає `carId = 1` (Toyota Camry); на «Бронюй Toyota Camry» передає `carId = 4`
   (Toyota Sienna). Чернетка створюється для іншого авто. Саме тут потрібне підтвердження людиною: картка показує
   назву й фото авто з бази, а не з тексту моделі, тож користувач бачить розбіжність до натискання «Підтвердити».
4. **Зайвий виклик для анонімного користувача (3.8-flash, 3.6-flash, B-05).** Користувач не увійшов, але 3.8-flash і 3.6-flash
   викликають `create_rental_draft`; інструмент повертає `authentication_required`, і модель коректно просить
   увійти. За датасетом це провал (заборонений виклик), але шкоди немає завдяки перевірці на сервері —
   приклад «захисту в глибину»: правила в промпті недостатньо, перевірка має бути в інструменті.
5. **Неоднозначне слово (gpt-oss, S-09).** «Потрібна механіка з 4 по 7 грудня»: gpt-oss-20b сприйняв запит як тему поза
   орендою авто й відмовив («можу допомогти лише з орендою автомобілів»); gpt-oss-120b виконав пошук, але загубив фільтр коробки передач.
   Gemini розпізнають «механіка» як механічну коробку.
6. **Без slot filling (E2, 3.5-flash-lite).** M-09: «Механіка до 1000 грн з 2 по 5 грудня» → «А з автоматом?» —
   у другому ході модель шукає без обмеження ціни, бо забула його; зі slot filling обмеження підставляється з пам'яті
   сесії. I-02: на «Потрібен автомат з 20 грудня» модель сама додає дату повернення 21 грудня й виконує пошук
   замість уточнення (зі slot filling у всіх трьох повторах запитала дату).
